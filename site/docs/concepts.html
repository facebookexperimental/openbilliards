Foundations

Concepts

Four ideas carry the whole SDK: one canonical binary, one scenario document, records made of events instead of frames, and a catalog of measured equipment. Everything else on these pages is surface area.

01 — Determinism & replays

Seed + params = bytes

The canonical physics is the committed wasm binary at web/dist/pool-wasm/, bit-exact across platforms because wasm float semantics are part of the spec. Servers, shares and replays use it; the native CLI and Python builds embed the same kernel source, and CI byte-compares one golden scenario across all three surfaces (native pool-cli, node TS SDK, pool_py) into identical record JSON scripts/cross-surface.sh.

Every record embeds its kernel_version (crate version + build hash) and format_version. Replay loading is strict on every surface: a record only replays on the build that made it, because cross-version replay is not bit-reproducible. Version gates are cheap; silently-wrong physics is not feature 005 (internal spec).

Shares follow the same doctrine: a share code carries the rack kind, seed, equipment ids and shot parameters, never frames, and the receiver re-simulates on the canonical wasm. A kernel mismatch is surfaced as a gate, not a decode error sdk/ts/src/share.ts.

02 — The scenario model

One document drives everything

Every surface consumes the same JSON document:

Scenario schema

{
  "system":  { "balls": [ … ], "table": …, "equipment": …? },  // SystemState
  "shot":    { "v0": 2.0, "phi": 1.5707, "theta": 0.0,
               "a": 0.0, "b": 0.0, "seed": 0 },                // ShotParams
  "options": { … }                                             // SimOptions, optional
}

The shot is a cue strike, not a velocity assignment: tip speed v0 (m/s, ≤ 15), azimuth phi, elevation theta, and tip offsets a/b in ball radii under the miscue limit a²+b² ≤ 0.25. The seed scopes all shot randomness. An omitted options key means the frozen v1 default physics; presets and equipment compose on top, they never mutate the default.

Input validation is kernel law, mirrored fast in the SDKs: unique ids with the cue (id 0) present and stationary, on-bed and airborne consistency rules, in-bounds positions, and a pairwise-overlap gate with a 1µm kiss tolerance sdk/ts/src/scenario.ts.

03 — Events & sampling

Events, not frames

The kernel is event-driven: it solves for the next collision or state transition analytically, resolves it, and snapshots the affected balls, looping until every ball rests. A ShotRecord is that event list plus the initial state: Strike, BallBall, BallLinearCushion, BallCircularCushion, BallPocket, BallTable, BallOffTable, Transition, then Rest the kernel contract.

Because motion between events is closed-form, a sampler reconstructs the exact state at ANY time; there is no fixed timestep to be between. All samplers share one flat layout: 8 floats per ball (x, y, z, qw, qx, qy, qz, motion_code), with the frozen code mapping 0 Stationary, 1 Spinning, 2 Sliding, 3 Rolling, 4 Pocketed, 5 Airborne. TypeScript fills a reusable Float64Array, Python returns numpy arrays, the CLI writes CSV: same bytes, three dialects.

Simultaneity is deterministic too: ties are broken by a frozen comparator (time, tier, energy, ids), so “the same break” is the same break down to the event order.

The rules layer builds on the same stream: a ruleset adjudicates each shot as a pure function of match state, the recorded event list and the recorded calls — no physics access, no re-simulation, no clock — so a replay produces identical verdicts on every machine. Which game adjudicates rides the share link (legacy links decode as 9-ball, never prompting), and the kernel stays game-agnostic: adding or editing a game entry changes zero physics ts · game catalog ts · rulesets.

04 — Equipment catalog

Measured equipment, pinned ids

Five axes (table, cloth, ball set, cue, cushion model) form one versioned registry in the kernel. Entries are immutable once shipped; new measurements get new ids, so a record's equipment tag stays meaningful forever. Every entry carries provenance: calibrated (fitted by this project), literature, or estimated the kernel contract · amendment 012.

All surfaces route through the same kernel resolve: table geometry at the ball set's radius, cloth friction applied to ball params, the cushion model slice (fitted models patch the table response; they are joint fits), the cue onto options, and the five-id tag onto system.equipment. The default composition is omitted from documents so byte parity holds.

Inspect it from any surface: engine.catalog(), pool_py.catalog(), or pool-cli catalog list; all three read the same registry cli · catalog.

05 — Kernel amendments

The changelog is a concept map

The kernel contract grows by numbered amendments; each one is a physics capability the SDK surfaces somewhere above the kernel contract · amendments.

  • 001 — selectable cushion model
  • 002 — airborne dynamics: 2.5D jump core, then true 3D airborne-vs-cushion and off-table terminal states
  • 003 — slip-velocity cushion friction hook
  • 004 — pinch-massé strike regime
  • 005 / 006 — Mathavan 2010 dual-contact cushion; separation clamp + step-size default
  • 007 / 008 — tangential-compliance bristle + e_x energy return; release energy-deficit cap
  • 009 — grip-mode stick-slip (cushion v5)
  • 010 / 011 — ball-ball micro-hop and ball-table bounce keep thresholds
  • 012 — equipment catalog: registry, spec resolution, cue on options
