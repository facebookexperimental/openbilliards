Getting started

The control layer of openbilliards is either an SDK or a UI: nothing else. TypeScript, Python and the command line all drive the same event-driven physics kernel through the same scenario document; none of them reimplements physics docs/sdk/README.md. Every example on these pages was executed against the shipped kernel before it was written down.

01 — One kernel, three surfaces

Pick your surface

The canonical physics is the committed WebAssembly binary at web/dist/pool-wasm/, bit-exact on every platform (Constitution canonical-binary doctrine). The native CLI and Python builds embed the same kernel source and CI byte-compares their records against the wasm on every platform.

SurfaceWhat it isRuns on
TypeScript SDK Typed wrappers over the canonical wasm: Engine, builders, records, per-frame sampling. node ≥ 20 and the browser, same glue
Python SDK PyO3 module pool_py: GIL-released batch simulation, numpy sampling. Built for analysis and RL loops. CPython ≥ 3.9, one abi3 wheel
pool-cli Native harness: run / batch / sweep / compare / sample / catalog over scenario JSON. anywhere cargo builds

02 — Install

Install & import

TypeScript. The SDK ships as plain ES modules in the repo: no package registry, no build step. Import the barrel from web/dist/pool-sdk/index.js (typed by the sibling index.d.ts) and point init() at the wasm glue web/dist/pool-wasm/pool_wasm.js. The same files work in node and in the browser; in node the SDK reads the sibling pool_wasm_bg.wasm from disk for you sdk/ts/src/engine.ts.

TypeScript — import paths

// browser (module script) or node ≥ 20 — same imports
import { init, ShotBuilder } from './web/dist/pool-sdk/index.js';

const engine = await init('./web/dist/pool-wasm/pool_wasm.js');

Python. pool_py builds from crates/pool-py with maturin into the active virtualenv; the abi3 wheel covers CPython 3.9 and newer crates/pool-py/README.md.

Shell — Python install

# development install, into the active venv (needs Rust + maturin)
cd crates/pool-py
maturin develop --release

# or build a wheel: one per platform covers CPython ≥ 3.9
maturin build --release      # target/wheels/pool_py-*.whl

CLI. One cargo build; use --release for batches.

Shell — CLI build

cargo build -p pool-cli --release
target/release/pool-cli version

03 — First simulation

Sixty seconds to a break

Rack nine balls from a seed, strike, and read the shot back. A ShotRecord is the complete, replayable result of one shot: every collision event plus enough state to reconstruct exact ball positions at any time. Same seed, same parameters: byte-identical record, on every machine concepts · determinism.

TypeScript — verified node 26, kernel 0.1.0+3856cb9

import { init, ShotBuilder, recordDuration } from './web/dist/pool-sdk/index.js';

const engine = await init('./web/dist/pool-wasm/pool_wasm.js');
const scenario = engine.nineBallRack(42);            // seeded, bit-identical rack
scenario.shot = new ShotBuilder().v0(9).phi(Math.PI / 2).seed(42).build();

const record = engine.simulate(scenario);            // typed, shape-validated
console.log(record.events.length, 'events,', recordDuration(record), 's');

const sampler = engine.sampler(record);              // playback index
sampler.sampleAt(0.5);                                // fills one reusable Float64Array
console.log(sampler.ball(0).motion);                  // cue ball at t = 0.5 s
sampler.free();

Output

144 events, 9.404100622978227 s
Rolling

The same sixty seconds in Python (the rack builders live on SystemState there):

Python — verified CPython 3.12, pool_py 0.1.0

import math
import pool_py as pp

state = pp.SystemState.nine_ball_rack(42)
shot = pp.Shot(v0=9.0, phi=math.pi / 2, seed=42)
record = pp.simulate(state, shot)
print(len(record.events()), "events,", record.duration, "s")

Output

98 events, 7.875108362178442 s

Note: the two outputs differ because the surfaces default differently: Engine.nineBallRack() templates carry the kernel's realistic options preset, while pool_py.simulate() with no options runs the frozen v1 default physics. Hand all surfaces the same scenario document and the record JSON is byte-identical; that cross-surface gate runs in CI scripts/cross-surface.sh.
