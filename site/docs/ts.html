Reference — node ≥ 20 · browser

TypeScript SDK

Typed wrappers over the canonical wasm kernel: load it once, build scenarios with kernel-identical validation, simulate to a replayable ShotRecord, and sample exact ball states at any time. The SDK exposes the kernel; it never reimplements physics sdk/ts/src/engine.ts.

01 — Loading the kernel

Loading the kernel

init(source, wasmBytes?)

init(source: string | URL | WasmGlueModule, wasmBytes?: BufferSource): Promise<Engine>

Load and instantiate the wasm kernel, returning an Engine. source is the glue module's path/URL (pool_wasm.js; the sibling pool_wasm_bg.wasm is found automatically: in node via node:fs, in the browser via the glue's own fetch) or an already-imported glue namespace. Double-init is safe: the glue caches its instance.

EngineError

Thrown when the kernel rejects a scenario with {"error": …}: malformed documents, rule breaches, unknown equipment ids.

KernelModule · WasmGlueModule

The raw wasm-bindgen surface the SDK wraps: kernel_version(), simulate_json(), new_rack_scenario(), catalog_json(), table_geometry_json(), WasmSampler. WasmGlueModule adds the default() initializer. You only need these types when passing a pre-imported glue namespace to init().

03 — Scenarios & shots

Building scenarios

A Scenario is the one JSON payload every surface shares: {system, shot, options?}. Build it fluently; build() validates with the same rules the kernel applies, so bad input fails fast with kernel semantics sdk/ts/src/scenario.ts.

TypeScript — verified node 26, kernel 0.1.0+3856cb9

import { init, ScenarioBuilder, ShotBuilder, realisticOptions }
  from './web/dist/pool-sdk/index.js';
const engine = await init('./web/dist/pool-wasm/pool_wasm.js');

const table = engine.table();                    // the kernel's WPA 9-ft geometry
const scenario = new ScenarioBuilder(table)
  .ball(0, { x: 0, y: -0.6 })                  // cue ball, on-bed at z = R
  .ball(9, { x: 0, y: 0.3 })                    // object ball up the long string
  .shot(new ShotBuilder().v0(2).phi(Math.PI / 2).tip(0, 0.3).build())
  .options(realisticOptions())                 // calibrated Stronge cushion
  .build();                                    // ValidationError on any breach
const record = engine.simulate(scenario);

Serialize a Scenario to the wire document accepted by simulateJson, pool-cli, and pool_py.

04 — Options & cloth

Options presets & cloth

FactoryPhysics
defaultOptions() Han 2005 cushion: the frozen v1 physics an omitted options key means.
realisticOptions() Stronge compliant cushion (ω-ratio 1.8) + footage-calibrated friction, the web app’s preset.

05 — Shot records

Shot records

A ShotRecord is {kernel_version, format_version, initial, shot, options, events, stats?}: the complete, replayable result of one shot. Each Event is {t, kind, post} where post snapshots the states of affected balls. EventKind is an externally-tagged union: 'Rest', Strike, BallBall, BallLinearCushion, BallCircularCushion, BallPocket, BallTable, BallOffTable, Transition sdk/ts/src/record.ts.

ExportDoes
FORMAT_VERSION = 1. Record schema version; parsing requires an exact match.
parseShotRecord(json, expectedKernelVersion?) Strict parse: format version must equal exactly; kernel version must match when given (cross-version replay is not bit-reproducible).
validateRecordShape(rec) Walks every field against the mirrored serde shapes and names the first drifted path.
recordDuration(record) Total simulated seconds: the final event time, 0 if empty.
RecordError Malformed JSON, version mismatch, or shape drift.
ShotStats Diagnostic counters (cushion_impacts_beyond_validity).

Precision caveat: shot.seed is a kernel u64 but a JS number: parseShotRecord REJECTS seeds above 2⁵³−1 rather than silently rounding. For foreign records, keep the raw JSON string and feed it straight to engine.sampler(json), the lossless path.

06 — Sampling

Sampling & playback

A Sampler reconstructs exact analytic ball states at any time, never resampled physics. It owns ONE reusable Float64Array, 8 slots per ball ([x, y, z, qw, qx, qy, qz, motion_code]), zero allocation per frame sdk/ts/src/sampler.ts.

MemberDoes
.sampleAt(t) Fill the buffer and return it. Before the first event → initial states; after the last → final states.
.data · .ballIds · .ballCount The flat buffer; ball ids in record.initial.balls order (stable); ball count.
.offset(i) · .ball(i) · .balls() Slot offset (8·i); decode one BallSampleView of the last frame; decode all (allocates).
.free() Release the wasm-side index when done.
FLOATS_PER_BALL = 8, the flat layout stride.
MOTION_CODES Frozen code → state mapping: 0 Stationary, 1 Spinning, 2 Sliding, 3 Rolling, 4 Pocketed, 5 Airborne.

Gotcha: MOTION_CODES buffer order (Pocketed = 4, Airborne = 5) differs from the MOTION_STATES type-declaration order. Decode buffer codes with MOTION_CODES, never by eyeballing the union.

09 — Beyond the barrel

Deep imports

Four modules are intentionally NOT exported from the frozen SDK barrel; consume them by deep import: the share codec (below), the game catalog (§10) and the rulesets (§11).

Share codec (share.js). A SharedGame (rack kind, seed, five-id equipment, shot list, cue-ball placements, game id, calls) is enough to reconstruct every record byte-for-byte on the same kernel version; replays re-simulate on the canonical wasm, never ship frames. SHARE_FORMAT_VERSION = 4 adds the game axis: game (a GameCatalog id) and calls (ShotAnnotation[] — per-shot pocket calls, safety declarations, and rulebook-decision resolutions; a decision at shotIndex k applies after shot k settles). v1/v2/v3 legacy shares still decode, always as game: 'nine_ball', calls: [] — never a prompt, and byte-frozen equipment mapping. MAX_RACK_SEED = 2³¹ keeps derived shot seeds (rackSeed·1000+shotIndex) safe integers sdk/ts/src/share.ts.

The multi-game Ruleset interface over these primitives is §11.

10 — Game catalog

Game catalog & rack templates

Five disciplines as data (games/index.js, a leaf module — deep import, never in the barrel). Every GameEntry carries full rulebook provenance (governing body, rulebook title, pinned edition, URL, transcribed sections) and a readiness tier. Since feature 012 all five entries are playable: each is bound to a shipped ruleset and a catalog table class, with empty prerequisite inventories (the config_ready tier remains in the type for future disciplines). Like equipment entries, game entries are immutable once shipped: a correction is a NEW id sdk/ts/src/games/catalog.ts.

11 — Rulesets

Rulesets — the multi-game referee

A Ruleset<S> is a pure referee over kernel ShotRecord events: verdicts derive exclusively from serializable inputs (prior match state, the event stream, recorded calls/decisions) — no re-simulation, no clock, no randomness. For identical inputs it returns deeply-equal outputs on every platform; order-of-events questions resolve by event-stream position, never by timestamp comparison sdk/ts/src/rules/index.ts.

Feature 013: judging is crate-backed — these modules keep their frozen 011/012 import paths, exports, and byte-identical verdicts, but delegate to the committed pool-rules wasm artifact. Nothing on this page changes; see the crate backing note below and the primitives guide docs/sdk/rules-crate.md.

TypeScript — verified node 26, kernel 0.1.0+5bd2803 (seed-7 break scratches)

import { init, ShotBuilder, scenarioToJson } from './web/dist/pool-sdk/index.js';
import { getGameEntry } from './web/dist/pool-sdk/games/index.js';
import { resolveRackTemplate, applyRackTemplate } from './web/dist/pool-sdk/games/rack.js';
import { getRuleset } from './web/dist/pool-sdk/rules/index.js';

const engine = await init('./web/dist/pool-wasm/pool_wasm.js');

// seeded WPA 4.2 rack: 8 centered, one solid + one stripe on the rear corners
const entry = getGameEntry('eight_ball');
const template = resolveRackTemplate(entry.rack_template);   // 'eight_wpa'
const scenario = JSON.parse(applyRackTemplate(
  template, scenarioToJson(engine.fifteenBallRack(7)), 7));
scenario.shot = new ShotBuilder().v0(8).phi(Math.PI / 2).seed(7000).build();
const record = engine.simulate(scenario);

// judge the break — a pure function of (state, record, call)
const rules = getRuleset(entry.ruleset_id);                  // 'eightball-v1'
const j = rules.judge(rules.initialState(1), record, null);  // break: no call, 4.3(a)
console.log(j.legal, j.fouls, j.decisionRequired);

// the incoming player exercises the 4.3(g) option: cue in hand in the kitchen
const state = rules.applyDecision(j.next, { decision: 4, choice: 2 });
const hud = rules.hudState(state);
console.log(hud.phase, '· shooter', hud.shooter, '· groups', hud.groups);

Judgment<S> · ShotCall · CitedFoul

Judgment is {legal, fouls, pocketed, ballInHand, respot, turn, decisionRequired, terminal, next}. Every foul is a CitedFoul {code, cite} — the rule number is data, not display copy (code doubles as the i18n key foul.<code>). ballInHand is a PlacementRight: 'none' | 'anywhere' | 'kitchen' | 'd_zone' (8-ball break fouls grant kitchen-only placement per 4.3(g),(h); standard fouls grant anywhere per 4.9; snooker in-hand is on or within the D — WPBSA Sec3 R8(a), feature 012). respot lists ball ids to return to their spots (pool: foot spot with the respotBallSpot long-string occlusion fallback; snooker and carom resolve through the discipline respot plans). terminal carries {winner, reason, cite}. next is the complete post-shot match state — a match replays as a left fold of (judge ∘ applyDecision) over the shot list and calls axis.

ShotCall is the per-shot rule input: {kind: 'call', ball, pocket} (pocket = kernel Table.pockets index, identical to the u16 in BallPocket events), {kind: 'safety'}, {kind: 'nominate', ball} (snooker colour nomination, ids 16–21 — share-codec calls-axis kind 3, feature 012), or null for games without call rules.

Shipped rulesets

nineball-v1 wraps the original judge (verdict logic byte-unchanged — the untouched nineball.test.ts suites are its oracle) onto the shared interface: call is always null, decisionRequired always null, respotNine maps to respot: [9]. nineballStateFromRecord(record, shooter) derives the wrapper state straight from a record.

eightball-v1 transcribes the WPA Rules of Play (eff. 2025-09-15) §4 with §3 fouls; every verdict carries its rule number. Call-shot mode is the strictest 1.7 reading: every non-break, non-safety shot MUST carry a call — a missing call is a RulesError (programming error), not a game foul; the break carries none (4.3(a)). EIGHTBALL_V1_CONFIG is frozen rulebook transcription, not house-rule toggles (threeFoulRule: false permanently, WPA 3.13 self-exclusion). Match state (EightBallMatchState) tracks phase (break/open/grouped/over), groups (solids 1–7 / stripes 9–15, assigned per 4.4), pending decisions and the foul context sdk/ts/src/rules/eightball.ts.

snooker-v1 (feature 012) transcribes the WPBSA Official Rules (Revised Sep 2024): red/colour ball-on sequencing through the final-colours endgame, penalty = clamp(4, value of ball on / ball concerned, 7) (Sec3 R11), colour nomination via {kind: 'nominate', ball} (a missing nomination on a colour shot is a RulesError, the 8-ball call convention), respot ids emitted highest-value first and never in final colours (Sec3 R3(h)(ii)), in-hand as 'd_zone' (Sec3 R8(a)), play-again (decision 7) and re-spotted-black toss (decision 8). Referee-judgment clauses (foul-and-a-miss R14, free ball Sec2 R13, touching ball R9, push stroke R18) are documented OUT of scope in the module header — nothing is invented. hudState surfaces {scores, currentBreak, ballOn, phase, penalty, respotQueue} sdk/ts/src/rules/snooker.ts.

carom3c-v1 (feature 012) transcribes the UMB World Rules (1 Jan 1989): a point requires the cue ball to contact ≥ 3 cushions before the SECOND object ball (Art 83), counted by event-stream position; an honest miss is legal: true, turn: 'pass' with the cited non-scoring reason insufficient-cushions in lastReason; the starting cannon must contact the red first (wrong-first-ball-break, Art 23.3/41.12); off-table balls respot via the Art 27.3(b)/28.1(b) spot-swap plan; race to a configurable target (settings data, never on the share wire). Physical-world fouls (Art 41.4–41.11) and the equal-innings format (Art 29.3/29.4) are documented OUT with cites. hudState surfaces {points, innings, target, cushionsThisShot} sdk/ts/src/rules/carom3c.ts.

onepocket-v1 (feature 012) transcribes WPA Rules of Play (eff. 2025-09-15) §12: break-pocket assignment with the 12.3 default (decision 6), own-pocket scoring with continuation, opponent-pocket balls counting for the opponent even on fouls (12.5), neutral-pocket and off-table balls queued to end-of-turn spotting (12.6), owed-ball debts (12.4), cue ball REMAINING after standard fouls with kitchen in-hand only for the 3.1 scratch (12.8), three consecutive fouls losing the rack (12.9), stalemate re-rack with tally carry-over and lag decision (decision 9; 12.10). hudState surfaces {tallies, owed, pockets, consecutiveFouls} sdk/ts/src/rules/onepocket.ts.

Crate backing (feature 013) · rulesVersion()

The rulesets above are one implementation, three surfaces: judging executes in the committed pool-rules wasm artifact (web/dist/pool-rules/ — a separate artifact from the physics wasm, with its own CI freshness gate), and the Python and CLI surfaces return the identical crate bytes. The TS loader uses module top-level await (the engine.ts dual-env precedent): the first rules/ import settles the wasm before any judge call — no init hook, no API change, and the frozen 011/012 modules (rules/index.js, the five ruleset modules, rules/respot.js) keep their paths and exports. Crate errors cross as structured payloads and re-throw as RulesError with the message verbatim.

rulesVersion() and rulesCatalogJson() (module rules/backend.js, the 013 introspection surface beside the raw conformance hook judgeRaw(id, state, record, call) in rules/index.js) return the rules build stamp 0.1.0+<git> — independent of the physics kernelVersion(), so rules iteration never repins the kernel — and the crate registry's catalog (every foul code, cite, and decision table). The primitives the crate is built from, and the worked money-ball example for composing a NEW game in ≤ 200 bespoke lines, are documented in docs/sdk/rules-crate.md.

12 — Layouts & respots

Discipline layouts & respot plans

games/layouts.js is the kernel-mirror layout data (drift-tested against the rack.rs constants): SNOOKER_LAYOUT — the six colour spots by ball id (16–21), baulk line, D radius and default cue address (WPBSA Sec1 R1(d)–(f)) — and CAROM_LAYOUT — top/centre/bottom spots and start-spot offset (UMB Art 11.6/22/23). colourValue(id) maps colour ids to point values (yellow 2 … black 7) sdk/ts/src/games/layouts.ts.

The respot planners in rules/respot.js are pure functions of layout data and final ball positions — placements are always DERIVED, never recorded, so replays resolve identically. snookerRespotPlan(layout, balls, ids) transcribes WPBSA Sec3 R7: own spot → highest-VALUE vacant spot → nearest centre-line point toward the top cushion, never touching another ball; multiple colours resolve highest first. caromRespotPlan(layout, balls, ids, shooter) transcribes UMB Art 27.3(b)/28.1(b): red → top, shooter’s ball → bottom, opponent’s → centre, with the occupied-spot swap rule — only the balls concerned respot. The pool helpers (respotBallSpot, respotNineSpot) are byte-unchanged sdk/ts/src/rules/respot.ts.
